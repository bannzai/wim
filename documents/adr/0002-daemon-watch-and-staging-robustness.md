# 0002. デーモンの watch・staging の堅牢化: 予約名前空間・有界 outbox・字句パス監視

## Status

Accepted

## Context

PR #30 (fs.watch) と PR #33 (原子的 write) への Codex レビュー指摘のうち、設計判断が要る点を issue #40 / #41 に繰り越した。個別に決めると意味論が食い違うため (staging の可視性と watch の readiness probe、symlink の監視意味論と #31 のパス閉じ込め)、ここでまとめて決める。

前提となる脅威モデルは ADR 0001 のとおり: デーモンは loopback + トークンで、守る相手は「同じマシンにいる、トークンを持たない別プロセス」。認証済みクライアントは信頼するが、その誤動作 (読まない・watch を張りすぎる) でデーモンや他の接続が壊れないことは保証したい。

## Decision

### 1. `.wim-` をデーモン予約の名前空間にする (issue #41-1, #40-2 の前提)

ルート配下でファイル名 (最終コンポーネント) が `.wim-` で始まるパスはデーモン内部の作業領域とし、クライアントから隠す:

- `fs.list` の結果から `.wim-*` エントリを除く
- watch のプッシュ (`fs.changed`) から `.wim-*` の変更イベントを除く
- リクエストのパスの最終コンポーネントが `.wim-*` のものは `permission_denied` (「予約名」) で拒否する。読み書きを許すと staging 名との衝突・すり替えの余地が生まれるため、隠すだけでなく触れなくする

write の staging ファイル (`.wim-<16hex>`) は既にこの名前空間にあり、後述の readiness probe もここに置く。トレードオフ: ユーザーが自分のファイルに `.wim-` 始まりの名前を使えなくなる。エディタ名を冠した隠しファイル接頭辞が第三者のファイル名と衝突する可能性は実用上無視できると判断した (Vim の swap の `.*.swp` と同種の慣習)。

### 2. watch イベントの outbox を有界にし、あふれたら接続を閉じる (issue #40-1)

接続ごとの outbox (レスポンスとプッシュが通る mpsc) を unbounded から有界 (容量 1024) に変える:

- **レスポンス** (セッションのリクエストループから送る): `send().await` で待つ。読まないクライアントへのバックプレッシャーがそのままリクエスト処理の停止になり、これが正しい流量制御になる
- **watch のプッシュ** (notify のコールバックスレッドから送る): コールバックはブロックできないため `try_send` する。満杯なら**その接続を閉じる**。イベントを黙って落とすと「watch は変更を必ず報告する」という契約が静かに破れ、クライアントは古い内容を正と信じ続ける。接続断なら再接続 + 再読み込みで一貫性が戻る (inotify の `IN_Q_OVERFLOW` が「取りこぼしたから再スキャンせよ」を明示するのと同じ発想。プロトコルに overflow 通知を足すのはワイヤ互換の変更になるため採らない)

容量 1024 の根拠: プッシュ 1 件は高々数百バイトで、1024 件 ≈ 数百 KB と接続あたりのメモリ上限として十分小さく、かつ FSEvents が再帰 watch 配下のビルドで出す瞬間的なバースト (数百イベント程度) を、読んでいるクライアントが吸収するには十分な深さ。

閉じ方: コールバックは `try_send` の失敗で共有の shutdown フラグ (`tokio::sync::Notify`) を立て、セッションの受信ループが `select!` でそれを拾って接続を終える。

### 3. watch 登録は readiness probe を待ってから応答する (issue #40-2)

FSEvents はストリーム開始直後の変更を取りこぼす window があり、`fs.watch` の成功応答が「以降の変更は報告される」を意味しない。応答の前に readiness barrier を置く:

- watch を登録した後、監視対象ディレクトリ (ファイル watch なら親ディレクトリ) に probe ファイル `.wim-probe-<random>` を create → remove し、その変更イベントが自分のコールバックに届くまで待ってから成功応答を返す。probe は予約名前空間にあるためクライアントのプッシュ・list には現れない (コールバック内では probe 判定をクライアント向けフィルタより先に行う)
- probe は 1 回ではなく **50ms 間隔で繰り返す**。ストリームが live になる前に作った probe は「遅れて届く」のではなく「失われる」(FSEvents の実測でストリーム開始まで 0.2〜4 秒かかり、その前のイベントは届かない) ため、1 回きりの probe は盲目の 2 秒待ちに退化する。繰り返しは barrier を実際の liveness 信号にし、平常時の応答も速くする
- probe が **2 秒**の予算内に観測できない場合は、そのまま成功応答を返す (best effort)。根拠: inotify / ReadDirectoryChangesW は登録と同時に有効で probe は即座に届き、FSEvents もレイテンシは既定でサブ秒。2 秒待って届かないのはイベント配送自体が極端に遅い環境で、そこで watch を失敗させるより「以降のイベントは遅れて届く」に倒す方が使える
- probe の create が権限等で失敗した場合も成功応答に倒す (読み取り専用ディレクトリの watch は正当な用途で、readiness の保証だけを落とす)

### 4. watch は字句パスで監視し、canonical 化は閉じ込め検査だけに使う (issue #40-3)

現状は `Root::resolve` が canonicalize したパスを watch するため、ルート内 symlink への `fs.watch` は実体側を監視し、symlink 自体の差し替え・削除が通知されない。監視の意味論を「名前を見る」に統一する:

- `fs.watch` の対象パスは字句的に解決する (ルート + `.`/`..` を取り除いた相対パス。字句的にルートを出るものは拒否)。canonicalize しない
- パス上に symlink がある場合、監視されるのはその名前の下で観測される変更であり、symlink の差し替え・削除はその名前の Removed/Created として届く。symlink の指す実体側で起きた変更は届かない (「名前を監視する」意味論)
- データアクセス (read/write/list) の閉じ込めは従来どおり canonical 検査で行い、その check/use race の解消は issue #31 (cap-std による beneath セマンティクス) が引き受ける。監視は読み書きを伴わないため、字句解決でルート外の情報が漏れることはない (watch イベントのパスはルート配下の名前で届く)

### 5. 接続ごとの watch 数に上限を設ける (issue #40-4)

`fs.watch` ごとに `RecommendedWatcher` (OS ハンドル + スレッド) を作る構造は維持し、接続あたり **64 個**で上限を設ける。超過は `invalid_request` 系のエラーで拒否し、メッセージで上限と `fs.unwatch` を案内する。

- backend watcher の共有 (1 接続 1 watcher に多重登録) は、イベントがどの watch のものかの帰属を再帰/非再帰の重なりの中でパス前置一致で判定し直す複雑さを持ち込む。上限で資源を抑えれば共有は不要と判断した
- 64 の根拠: エディタセッションが張る watch は開いているファイル + 作業ディレクトリ程度で 1 桁〜2 桁前半。64 は対話利用の上限として十分大きく、1 watcher が使う OS 資源 (FSEvents ストリーム / inotify fd / スレッド) × 64 × 接続数はローカルデーモンの許容範囲
- 接続数自体の上限は設けない (トークンを持つクライアントしか watch を張れず、ADR 0001 の脅威モデルで接続爆発は守備範囲外)

### 6. 書込不可ディレクトリ内の既存ファイルへは in-place write にフォールバックする (issue #41-2)

staged + rename は親ディレクトリへの書込権限を要求するため、`0555` のディレクトリ内にある `0644` のファイル (旧実装の直接 `fs::write` なら更新できた構成) が書けなくなる。staging ファイルの作成が `PermissionDenied` で失敗し、**かつ書き込み先のファイルが既に存在する**場合に限り、そのファイルを開いて `truncate` + 書き込みする in-place write にフォールバックする。

- 原子性のトレードオフ: in-place write はクライアントが読む当のファイルを切り詰めてから埋めるため、途中で失敗すると新旧どちらでもない内容が残り得る。書けないより書ける方を採る判断で、Vim の `backupcopy=yes` が同じ理由で払うコストと同じ
- 新規作成には適用しない (`create` を付けない)。書込不可ディレクトリに新しいファイルは作れないため、フォールバックで write の意味論を広げない。存在しないパスへの write は従来どおり失敗する
- フォールバック自体が失敗した場合は、そのエラー (最後に実際に試みた書き込みのもの) を返す

## Consequences

- `.wim-*` はクライアントから見えず・触れない名前になる (ワイヤ上のメソッドは不変。`fs.list` / `fs.changed` の結果からの除外とパス拒否はサーバー側の意味論)
- 読まないクライアントは watch のバーストで切断され得る。再接続 + 再読み込みが回復手順
- `fs.watch` の成功応答は「以降の変更は報告される」を (best effort で) 意味するようになる。ただし実測で FSEvents のストリーム開始が 2 秒の予算を超えることがあり (約 4 秒の観測例)、その場合は best effort に倒れるため、E2E の変更リトライは保険として残す (`crates/wim-daemon/tests/e2e.rs` の `CHANGE_RETRY` に測定値を記録)
- symlink への watch は名前の監視になり、実体追跡が欲しいクライアントは実体パスを watch する
- issue #31 (cap-std) はこの ADR の 4 を前提に、read/write/list の閉じ込めだけを置き換える
- write の原子性は「staging が作れる限り保証される」になる。書込不可ディレクトリ内の既存ファイルへの write だけは非原子的な上書きになり、失敗時に中途半端な内容が残り得る
