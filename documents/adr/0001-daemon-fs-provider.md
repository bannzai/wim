# 0001. デーモンは FS プロバイダに徹し、編集バッファはクライアント側に置く

## Status

Accepted

## Context

wim はモーダル編集コア (`crates/wim-core`) を 1 つの pure crate にし、headless CLI / デーモン / ブラウザ (Wasm) の 3 形態で同じコアを動かすことをポジショニングの核にしている (`documents/PROJECT.md`)。

Phase 2 でローカル / リモート共通のデーモンを導入するにあたり、デーモンとクライアントの責務の境界をどこに引くかを決める必要がある。境界の引き方でクライアント側の構造・編集レイテンシ・将来のブラウザ UI の実装量が変わり、後から変えるとプロトコルとクライアント双方の作り直しになる。

あわせて、その境界を越えるプロトコル (トランスポートとシリアライズ形式) と、デーモンへの接続の認証方式も決める必要がある。

## Decision

### 検討した選択肢: バッファをどちら側に置くか

**選択肢 A: デーモン側でバッファを動かす。** デーモンが `wim-core` の `Editor` を保持し、クライアントはキー入力を送って描画に必要な状態を受け取る端末に徹する構成。

**選択肢 B: デーモンは FS プロバイダ (open/read/write/list/watch) に徹し、バッファはクライアント側で動かす。** デーモンはファイルの内容と変更通知だけを提供し、`wim-core` の `Editor` は各クライアントが自分で持つ構成。VS Code Remote の `FileSystemProvider` と同じモデル。

**選択肢 B を採用する。**

理由:

- **コアの配置を 3 形態で揃えられる。** Phase 3 のブラウザ UI は Wasm でコアをクライアント側に持つ設計が確定している (JS ⇔ Wasm 境界は「キー入力を渡してダメージ領域を返す」粒度。`documents/PROJECT.md`)。選択肢 A ではブラウザ形態だけコアの配置が反転し、「クライアントにコアがある」統合層と「デーモンにコアがある」統合層の 2 系統を維持することになる
- **編集レイテンシがネットワーク遅延から切り離される。** 選択肢 A はキーストローク毎に RTT が乗り、リモート編集での遅延が編集操作そのものの体感に直結する。選択肢 B ではネットワーク遅延が open / save / watch の境界にだけ現れる
- **デーモンの責務が小さくなる。** 提供するのはファイル操作と変更通知だけで、モード・レジスタ・undo 履歴といった編集状態をデーモンが持たずに済む

### 検討した選択肢: プロトコル

WebSocket text frame 上の JSON を採用する。メッセージの形は次の 3 種類で、全メッセージがバージョンフィールド `v` を持つ。

- リクエスト: `{"v":1,"id":N,"method":"...","params":{...}}`
- レスポンス: `{"v":1,"id":N,"result":...}` または `{"v":1,"id":N,"error":{...}}`
- サーバープッシュ: `{"v":1,"event":"...","params":{...}}`

理由:

- **デバッグが容易。** ワイヤ上の内容がそのまま読め、`wscat` 等の汎用ツールで手で叩ける
- **`serde_json` が成熟している。** デーモン (ネイティブ) とブラウザクライアント (Wasm) の双方で同じ型定義をそのまま使える
- **性能差が問題にならない粒度。** やり取りはファイル単位のペイロードであり、キーストローク単位ではない。JSON のシリアライズコストが編集体験に効く場面がない

全メッセージに `v` を持たせることで、バイナリフレーム上の msgpack へ将来移行する余地を残す。移行時は `v` を上げ、旧バージョンのクライアントを識別して拒否または互換処理ができる。

### 検討した選択肢: 認証

デーモンは 127.0.0.1 に bind する (デフォルト)。起動時にランダムトークンを生成して stdout に表示し、クライアントは接続後の最初のメッセージ `{"v":1,"id":0,"method":"auth","params":{"token":"..."}}` でそれを提示する。トークンが一致しない接続は即座に切断する。

理由:

- loopback bind により、同一マシン上のプロセス以外からは到達できない
- 同一マシン上の他プロセスからの接続に対しては、起動時トークンが防御になる
- リモート利用は SSH トンネル前提とし、Phase 2 のデーモンは TLS を持たない。転送路の暗号化と認証は SSH に委ねる

## Consequences

- クライアントは自分でバッファを持つため、`wim-core` をリンクできる形態 (ネイティブ CLI / TUI、Wasm ブラウザ) でのみデーモンを利用できる。薄い端末だけを置く運用はできない
- デーモンとクライアントが共有するメッセージ型は独立した pure crate (`crates/wim-protocol`) に置き、`wasm32-unknown-unknown` でビルドできる状態を維持する (IO・tokio を入れない)
- **複数クライアントの同時編集の整合はデーモンが担わない。** Phase 2 は last-write-wins と watch による変更通知までとする。同じファイルを 2 つのクライアントが開いた場合、後から書いた方の内容が残る。競合解決や OT / CRDT が必要になった時点で別の ADR で扱う
- 認証は起動時トークンのみのため、デーモンを loopback 以外に bind する運用は Phase 2 では想定しない。公開ネットワークへ出す場合は SSH トンネルを使う
- ワイヤ表現 (`v` を含む JSON の形) は `wim-protocol` の公開契約になるため、JSON 文字列そのものを固定するテストで守る
