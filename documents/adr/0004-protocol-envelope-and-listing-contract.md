# 0004. wim-protocol のワイヤ契約を 4 点明確化する (最小エンベロープ・id 無しエラー・EntryKind::Other・fs.list の子パス)

## Status

Accepted

## Context

PR #27 への Codex レビュー指摘 4 点を issue #32 に繰り越したもの。いずれも wim-protocol のワイヤ表現 (公開契約) に関わるため、まとめて設計判断する。

前提: プロトコルは v1 で未リリース。クライアントは全てこのリポジトリ内 (web/daemon.js と各テスト) にあり、リポジトリ外に配布済みのクライアントは存在しない。互換性の扱いはこの前提の上で決める。

## Decision

### 1. バージョン判定は最小エンベロープの 2 段デシリアライズにする

将来バージョンが新 method やパラメータ変更を持つと、`Request` への一括デシリアライズは `v` を見る前に失敗する。デーモンは raw JSON から `v` を先に手読みして正しく `unsupported_version` を返せていたが、この保証はデーモンの実装詳細で、プロトコルの契約としてはどこにも固定されていなかった。

- wim-protocol に `Envelope` 型を追加する。`version: Option<u64>` (`v`) と `id: Option<u64>` だけを持つ Deserialize 専用の型で、バージョン固有の部分 (method / params / result / error) は読まない
- 受信側の契約: まず `Envelope` を読む → `v` が読めて未対応なら `unsupported_version` を envelope の id で返す → 対応版の時だけ `Request` をデシリアライズする
- `version` を `u64` で読むのは、`u32` に収まらない `v` も「ゴミ」ではなく「話せないバージョン」として答えるため (`is_supported_version` は従来どおり `u32`)
- 「v2 + 未知 method のメッセージが `Envelope` としては読め、`Request` としては読めない」ことをテストで固定し、デーモンの raw JSON 手読みをこの型に置き換える

### 2. id が読めないメッセージには id 無しのエラーエンベロープで答える

`Response` は `id: u64` 必須のため、id 欠落・非数値の不正メッセージには id=0 で代用しており、進行中リクエスト id=0 と誤マッチし得た。

- `Response.id` を `Option<u64>` にし、無い時はワイヤに `id` を出さない: `{"v":1,"error":{...}}`
- `Response::err_unmatched` を追加する。`Envelope` すら読めないメッセージ (JSON でない、`v` や `id` の型が不正) への応答はこれで返す
- 捨てた案:「id 0 は未対応付けエラー用に予約」。ADR 0001 が auth の例として id 0 を明記しており (`{"v":1,"id":0,"method":"auth",...}`)、既存クライアント (web/daemon.js) も 0 起点の連番で 0 を正当な id として使っている。予約は配布済みの意味の書き換えになる
- id 無しの応答はどのリクエストとも照合されない。web/daemon.js は id が引けない応答を既に無視するため、挙動は壊れない

### 3. EntryKind に Other を追加する

`EntryKind` は File / Directory / Symlink のみで、socket / FIFO / device を表せず、デーモンは File に誤分類していた。

- `Other` (ワイヤ名 `"other"`) を追加し、regular file・directory・symlink のいずれでもない子はこれで報告する。デーモンの分類も `is_file()` を明示的に見る形に直す
- 互換性: v1 は未リリースでクライアントは全て同一リポジトリ内のため、v1 の範囲内で追加する。v1 を出荷した後の列挙追加はバージョンを上げる変更になるが、`Other` が「それ以外」を全部吸収するため、以後この列挙に新しい値を足す必要自体がなくなる (閉じた列挙になる)
- 捨てた案: 非通常ファイルを listing から除外するポリシーの明文化。`FsListResult` の「direct child 1 つにつき 1 エントリ」という約束が壊れ、クライアントからディレクトリの実態が見えなくなる

### 4. fs.list の子エントリはデーモン native の完全パスを持つ

`DirEntry` は名前のみで、クライアントはデーモンのパス構文 (区切り文字・結合規則) を知らないと子パスを合成できなかった。Phase 3 のブラウザクライアントには合成の手段がない。

- `DirEntry` に `path: Option<String>` を追加する。デーモン自身のパス構文での完全パスで、そのまま `fs.read` / `fs.list` / `fs.watch` の `params.path` に渡せる。`name` は表示用として残す
- パスが UTF-8 でない子 (unix はファイル名に任意のバイト列を許す) は、エントリとしては列挙しつつ `path` を持たない (ワイヤに `path` キーを出さない)。JSON 文字列は任意バイト列を無変換では運べず、U+FFFD で埋めたパスは別のファイルか存在しないファイルを指すため。`fs.read` が非 UTF-8 の内容をバイト列ではなくエラーにするのと同じ姿勢で、可逆なバイト列表現 (base64 等) の発明は第二のパス表現と同じ理由で採らない (PR #74 discussion_r3906419450)
- 捨てた案: プラットフォーム非依存のパス表現 ('/' 区切りのルート相対パス等) の定義。クレートは「パスはデーモンのもので、パースも正規化もしない」を既に宣言しており、`fs.changed` の push も native の絶対パスを運んでいる。第二のパス表現を導入すると、クライアントに 2 表現の変換の知識が要り、watch が push するパスとの照合も崩れる。native 完全パスなら、クライアントはパスを不透明なトークンとして扱うだけで合成が不要になる

## Consequences

- クライアントはディレクトリを辿る時、名前からパスを合成せず `entry.path` をそのまま次のリクエストに使う。ブラウザクライアントはデーモンの OS のパス構文を知らなくてよく、`fs.changed` が運ぶパスと同じ表現で照合できる
- 将来版のメッセージに v1 実装が `unsupported_version` で答えられることが、実装詳細ではなく型とテストで保証される
- id 無しエラーはどのリクエストの応答でもないため、クライアントは無視してよい (診断・ログにだけ意味を持つ)。`Response.id` が `Option` になるのは Rust API 上の変更で、正常応答のワイヤ表現は変わらない
- socket / FIFO / device が `"other"` として見えるようになり、ワイヤ表現としては v1 内の追加になる (前提のとおり、壊れる配布済みクライアントは無い)
